## Контекст (прочитай — не пропускай)

Система AFES торгует FX stat-arb парами на FundingPips Zero ($5,000, 3% daily loss = $150/день).
Экспертный анализ выявил два фундаментальных конфликта с текущими параметрами:

**Конфликт 1 — Sizing убьёт счёт быстрее рынка:**
`TARGET_RISK_USD = 150` = 1σ риска на сделку.
При ENTRY_Z=2.0 и STOP_Z=3.5 → убыток до стопа ≈ 1.5σ ≈ $225 на одну сделку.
$225 > $150 дневного лимита. Один стоп = breach. Это не риск — это математическая
гарантия нарушения правил пропа при первом же неудачном дне.

Правильная формула: `TARGET_RISK_USD ≤ daily_limit / (max_losers_per_day × stop_R)`
= 150 / (3 × 1.5) ≈ 33. С буфером на taker costs и до 4 одновременных позиций → 20.

**Конфликт 2 — Частота убита слоями фильтров:**
8 hard-block фильтров + macro HMM (блокирует 49% баров) + velocity (убивает 65% входов).
Результат: gap между сделками = 4000+ дней при лимите 30 дней.
Velocity gate математически доказано фильтрует ЛУЧШИЕ входы (Sharpe 37 vs 27).
Copula, RVOL, Session — дублируют защиту которая уже обеспечена Hurst + innov_var + live_corr.

**Важное архитектурное замечание (не чинить сейчас — просто знать):**
`zero_account_report()` считает PnL только по реализованным выходам (step4a_backtest.py:1135),
не по intraday MTM. На live реальный риск будет выше чем показывает backtest-report.
Это ограничение backtester — не баг который надо чинить в этом промпте.

## Фаза 1: Контроль риска (делать ПЕРВЫМ — защита от blow-up)

### Изменение 1.1
```python
# БЫЛО (строка 228):
TARGET_RISK_USD = 150.0

# СТАЛО:
TARGET_RISK_USD = 20.0   # Zero-safe: суммарный stop-risk 4 позиций = $80 < $90 буфера
```
**Почему 20**: 4 пары × $20 × 1.5 stop_R = $120 total daily stop-risk. Остаток $30 — буфер
на taker costs и slippage. Это единственное число которое не нарушает $150 даже при
максимальной загрузке книги.

### Изменение 1.2
```python
# БЫЛО (строка 208):
PAIR_MAX_LOSS = -1500.0

# СТАЛО:
PAIR_MAX_LOSS = -75.0    # Zero-safe: одна "сломанная" пара не съест trailing buffer $250
```
**Почему -75**: trailing drawdown limit = $250. Одна пара не должна иметь право потратить
больше 30% от этого лимита прежде чем её отключат. -75 = 30% × $250.

## Фаза 2: Разблокировка частоты (делать ВТОРЫМ — после риск-контролей)

### Изменение 2.1
```python
# БЫЛО (строка 123):
USE_VELOCITY_GATE = True

# СТАЛО:
USE_VELOCITY_GATE = False   # доказано: блокирует first-touch входы с Sharpe=37 vs 27
```

### Изменение 2.2
```python
# БЫЛО (строка 143):
SESSION_FILTER = True

# СТАЛО:
SESSION_FILTER = False   # 24h FX + event_blackout уже покрывает новостные риски
```
**Почему**: SESSION_FILTER при round-the-clock FX с уже работающим EVENT_FILTER = двойная
защита без дополнительного edge. Убивает ночные сессии (Азия/Тихий океан) где FX пары
тоже дают валидные mean-reversion сигналы.

### Изменение 2.3
```python
# БЫЛО (строка 151):
USE_COPULA = True

# СТАЛО:
USE_COPULA = False   # дублирует live_corr + kalman_innov; вычислительно дорого
```
**Почему**: Copula confirmation проверяет зависимость хвостов. Это уже покрыто:
`LIVE_CORR_FILTER` (текущая корреляция), `KALMAN_INNOV_FILTER` (стабильность коинтеграции),
`HURST` (mean-reversion природа спреда). Тройная защита — одна достаточна.

### Изменение 2.4
```python
# БЫЛО (строка 106):
USE_RVOL_GATE = True
# БЫЛО (строка 107):
RVOL_THRESHOLD = 0.75

# СТАЛО:
USE_RVOL_GATE = True          # оставляем но ослабляем — защищает от иллюквидных часов
RVOL_THRESHOLD = 0.60         # 60% вместо 75% — менее агрессивный отсев
```
**Почему не выключаем полностью**: RVOL gate защищает от входов в thin market (азиатская
сессия в праздники, flash crash window). Снижение с 0.75 до 0.60 даёт +20–25% пропускаемых
баров при сохранении защиты от совсем иллюквидных периодов.

## Фаза 3: Настройка сигнала (делать ТРЕТЬИМ — после того как частота разблокирована)

### Изменение 3.1
```python
# БЫЛО (строка 74):
ENTRY_Z = 2.0

# СТАЛО:
ENTRY_Z = 1.8    # +~35% входов без потери edge; 1.8/0.5 даёт те же 2.3σ ожидаемого отката
```

### Изменение 3.2
```python
# БЫЛО (строка 75):
EXIT_Z = 0.3    # exit before full mean reversion (lock in profit faster)

# СТАЛО:
EXIT_Z = 0.5    # быстрее фиксируем прибыль → больше profitable days для Zero
```
**Почему**: Zero требует 7+ прибыльных дней/месяц, не максимального PnL на трейд.
1.8 (entry) - 0.5 (exit) = 2.3σ ожидаемого отката — идентично старому 2.0 - 0.3 = 2.3σ.
Те же ожидания, но прибыль фиксируется раньше = больше закрытых в плюс дней.

### Изменение 3.3
```python
# БЫЛО (строка 76):
STOP_Z = 3.5

# СТАЛО:
STOP_Z = 3.2    # сужаем стоп соразмерно уменьшению TARGET_RISK_USD
```
**Почему**: при TARGET_RISK_USD=20, стоп на 3.5σ означал бы ~$35 убытка.
3.2σ → ~$28 — более tight при маленьком риске на сделку. Сохраняет R:R ≈ 1.3.

### Изменение 3.4
```python
# БЫЛО (строка 77):
ENTRY_Z_MIN = 1.8    # floor for grid search

# СТАЛО:
ENTRY_Z_MIN = 1.7    # floor на 0.1 ниже нового ENTRY_Z — оставляем пространство для WFO
```

### Изменение 3.5
```python
# БЫЛО (строка 226):
MAX_PAIR_WEIGHT = 0.15

# СТАЛО:
MAX_PAIR_WEIGHT = 0.10   # max notional на пару: $5000 × 0.10 × 50 = $25,000
```
**Почему**: при 4 парах и MAX_PAIR_WEIGHT=0.15 суммарный notional = 4 × $37.5K = $150K.
С 0.10 → 4 × $25K = $100K. Сохраняем leverage при уменьшении концентрационного риска.

### Изменение 3.6
```python
# БЫЛО (строка 221):
MIN_POSITION_SIZE = 0.15

# СТАЛО:
MIN_POSITION_SIZE = 0.10   # HMM_PANIC_MULT=0.333 × другие multipliers иногда даёт 0.12-0.14
```
**Почему**: с исправленным HMM и macro_alert, combined sizing_multiplier в panic режиме
может быть 0.333 × 0.3 = ~0.10. Без этого изменения все panic-период входы пропускались бы.

## Если max_inactive_days всё ещё > 30 после всех изменений

Это означает проблему в universe (мало пар), не в параметрах.
В этом случае следующий шаг — расширить число пар-кандидатов в `pairs_selected.csv`,
а не снижать ENTRY_Z ниже 1.7. Снижение до 1.5 без расширения universe = curve-fitting.
